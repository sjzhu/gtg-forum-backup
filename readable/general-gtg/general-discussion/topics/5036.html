As a way to practice making dynamic websites with Cold Fusion, I’ve made online versions of Risk (pretty easy) and Heroclix (much more difficult). The app enforced the rules of the game and tracked the game state. It was a great system which allowed my friends and me to set up a number of concurrent games and whenever we had time during our work day we’d log on, take our turns, then log off so the next guy in the turn sequence could take theirs. We wasted a lot of time at work that way…

That asynchronous gameplay, where your buddies didn’t have to actually be online with you at the same time, was one of the best and worst things about them. On the one hand, it made it so that you could participate in multiple games with your friends who could take their turns whenever they had time throughout the day, and so was very convenient that way. On the other hand, this kind of a thing would only work for games that required no actual interaction between players on any given turn (Risk has the tiniest bit of interaction in that a defender can choose to roll one or two dice, but I just automated it to choose the max number of dice possible to roll in every case so that the off-turn choice was eliminated).

Second on the downside was that the game’s rules had to be something that was moderately possible for me to automate. For example, each unit in Heroclix has (had, since I understand it’s gotten more complicated over time) a set number of abilities at each point along their dial, and each ability did a set thing, so that as long as I knew the position of each piece on the board and what tey could do at their current dial position, I was mostly set. Contrast that with a game like Magic: the Gathering, which is a game where every card does something very different from every other card. I could spend my whole life coding the rules for each card and still never be done.

What does any of this have to do with anything? I’ve considered the feasibility of trying to make a SotM online game like my others. On the plus side, while there is collaboration in decision making, only one player can actually take an action at a time, on their turn. There is no case where someone plays a card or chooses to activate an ability on someone else’s turn. So that’s good. But on the negative side, SotM is a lot like M:tG in that the rules on each card can do their own thing, and coding a game where every card has a unique set of rules to it would be tough. That’s what has kept me from starting the project so far, at least.

If I can figure out a way to make it work, I might still give it a try.

I’ve been giving this issue (an online way to play) more thought than I should while at work today. Here’s me thinking out loud about how to possibly build the solution we’re looking for. I see two possible paths:

(a) your game has a backend (for example: ASP or ColdFusion with a database) to store the state of the game. pros: since the state of the game is stored on the server, everyone will always be able to view the same state as long as they use their “refresh” button. cons: someone would have to host the database (tying everything to a single person, which isn’t great), if the server went down so does the game, and having to post and get info to/from the database every time any change is made in the game means that you’ll spend a lot of time watching your browser refresh. I remember with my online games, I’d often get calls from my friends asking me to go into the admin panels of the game to adjust how many armies were in each territory because someone had made a move but their browser crashed in the middle of it so the database was wrong. That’s not a good way to go.

(b) your game has no backend (it’s just html and javascript). pros: anyone who can take the game’s files and toss them on their server can host the game. cons: because there’s no backend, there’s no shared state of the game for everyone to view.

The best way around this that I’ve been able to come up with so far is to have the URL contain parameters storing the state of every card in the game. It would make for a loooong URL, but is doable. Whenever a change is made (someone draws or discards, for example), they hit an “update” button which refreshes the view with the new URL. Then they send that new URL to everyone in the game so that everyone is on the same page again.

This sounds like a pain to me, but I can’t think of a better way to go. One other advantage of this method would be that you could “save” the game at any time. If you need to end the game but you want to pick it up later, you can just copy the URL and then paste it later into your browser. Boom, the game is set up exactly as it was when you left it. One other disadvantage to this though is that since you’re only maintaining the state of the game as it exists at any given point, the only way to maintain a history would be for someone to paste each new URL into a text document or something so that if you needed to go back a turn or two for some reason, you could do that. Like I said, sounds like a pain, but I don’t see many alternatives.

Just a heads up, I was bored a couple of weeks ago and decided to see if I could put together a web page that would allow people to play SotM online together. It’s not finished yet, but I’m far enough along to be able to say that it most likely will be finished and will most likely do what I built it to do (neither of which are granted when you start a project like this).

What I’m building it to do is the following:

  1. allow a user to select a set of heroes, a villain and an environment to begin a game.
  2. the game will handle all card management, meaning that it will allow the user to shuffle cards, draw cards, and allow users to move cards between areas (deck, discard, hand, table).
  3. the game will keep track of hero & villain hp as well as their normal/flipped state. It will also keep track of each card’s hp, if the card has hp.
  4. it will NOT make any decisions based on rules or card text. If the user decides that Bunker blasts the villain and a couple of minions with a Grenade Launcher, the user will change the dropdown that tracks each of those card’s hp themself.
  5. all of the game’s data will be stored in the page’s URL so that if a group of friends are on Skype or whatever, they can take their turn by moving cards from their hand to the table, changing hp for targets that have been attacked, move cards from the table to discard when they’re destroyed, etc. and then hit “submit”. They can then IM the resulting URL to everyone in the Skype session and everyone else can load that page and so view the same game state as everyone else.

The reason I’m mentioning it before it’s done or before I’m even ready for anyone to take a look at it is because of the ethical issues we’ve discussed here before, i.e. anyone with my web page could play SotM without having paid for it, which I’m not comfortable with. If some kind of solution (or rationalization) can’t be found, I won’t be releasing this thing to the wild. But if we can find a way to do the right thing, then maybe people will be able to use this tool to play this fun game with a geographically diverse group of friends, which would be nice.

And it will be used via web browser which means it can be used via an iPad

Well, here’s where my implementation will be weakest. I’ve tested it on an iPad, and since it’s basically just a web page, it works great (some of the buttons are a little easy to fat-finger, but that’s fixable), especially as a solo experience. The problem is with multiplayer because of how I’m building it:

My main design goal is to have it be self-contained, meaning that there’s no database or backend system that I need to maintain to store game-state. But the data describing the current game-state needs to be stored somewhere. I’m storing it in the URL, which has a few advantages: (a) it’s easy to do, (b) the browser will maintain a history so I don’t have to, (c) you can save a game and come back to it later by copy/pasting the URL somewhere and then going back to it, (d) you can have multiple games going on concurrently by having multiple browser windows that use different URLs.

There’s a big disadvantage to this method though. Everyone in the game has to have access to the same URL to be able to view the same game. That means play will go something like this:

Everyone’s on Skype, having fun chatting. Someone takes their turn, hits “submit”, gets a new URL showing the updated game-state. They copy/paste the URL into a shared IM window. Everyone else in the game copies it into their browser window and now everyone’s on the same page again. Repeat every time someone takes their turn or updates the game-state.

This is in no way elegant, and I don’t love it. But given my main design goal (see above), I haven’t been able to think of a better way. A friend of mine suggested using Dropbox to store a file containing the game-state data which the game reads and then updates every time someone hits “submit”, which would make it so that all anyone would have to do is announce over Skype “k, done. refresh” and when everyone refreshed their browser, it would fetch the updated data. This has got its own problems though, could end up being an even greater pain in the kiester to implement, and may not even work anyways. So at the moment, sharing URLs is my plan of record.

Which brings me around to why I’m saying all of this in the first place. If you think copy/pasting a URL 100 times during the course of a game on a computer is a pain, doing it on an iPad will be 10x worse…
